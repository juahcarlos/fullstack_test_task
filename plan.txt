## 1. Аудит и список переделок

### Backend

# План реализации (backend)

1. **Конфигурация**
   Собираем через `pydantic-settings` вместо разбросанных `os.environ.get()` — валидация, типизация, единая точка изменения при деплое.
   `backend/src/app/core/config.py`

2. **Инициализация БД**
   Engine и sessionmaker выносим в отдельное место, сессия становится зависимостью FastAPI (`Depends`), а не модульным side-effect'ом при импорте — так сессию можно подменить в тестах.
   `backend/src/app/core/database.py`

3. **DI-алиасы**
   Оборачиваем зависимости (сессия, сервисы) в `Annotated`-алиасы — чтобы не повторять `Depends(...)` в каждой сигнатуре и чтобы сервисы можно было мокать в тестах.
   `backend/src/app/core/dependencies.py`

4. **ORM-модели**
   Переносим без изменения полей и связей — бизнес-логику/схему БД не трогаем.
   `backend/src/app/models.py`

5. **Pydantic-схемы**
   Переносим без изменений — валидация ответов остаётся той же.
   `backend/src/app/schemas.py`

6. **Repository-слой + Unit of Work**
   Выделяем слой доступа к БД: `BaseRepository` — обобщённый CRUD поверх произвольной модели, устраняет дублирование между `FileRepository`/`AlertRepository`, а также между FastAPI-роутами и Celery-таском, которые в исходном варианте независимо дублировали одни и те же операции с моделями. Управление транзакцией (commit/rollback) вынесено из репозиториев в отдельный `UnitOfWork` — единая точка для FastAPI (через DI) и Celery-таска, вместо того чтобы каждое место коммитило сессию самостоятельно.
   `backend/src/app/repositories.py`, `backend/src/app/core/uow.py`

7. **Сервисный слой**
   Бизнес-логика (создание/обновление/удаление файла, лимит размера, санитизация имени, листинг с пагинацией) — принимает зависимости через конструктор, чтобы это можно было тестировать без реальной БД/диска.
   `backend/src/app/services.py`

8. **Роуты**
   Делаем тонкими — только вызывают сервисы через DI, без логики внутри.
   `backend/src/app/api/files.py`, `backend/src/app/api/alerts.py`, `backend/src/app/api/router.py`

9. **Оптимизация Celery**
   Три отдельных таска (скан → метаданные → алерт) объединяем в один, работающий через единую транзакцию `UnitOfWork` — убираем три round-trip'а в Redis и три отдельные транзакции ради одной последовательной операции. Это и есть оптимизация из ТЗ.
   `backend/src/app/tasks.py`

10. **Потоковое чтение файлов**
    Извлечение метаданных (подсчёт строк/страниц) делаем потоковым там, где возможно, а не загружаем файл в память целиком.
    `backend/src/app/tasks.py`

11. **Харденинг аплоада**
    Лимит размера загружаемого файла и санитизация оригинального имени файла перед использованием в ответе — сейчас это не контролируется.
    `backend/src/app/services.py`

12. **Unit-тесты**
    На сервисный слой с моками зависимостей — демонстрируем тестируемость архитектуры (сверх требований ТЗ).
    `backend/tests/unit/`

13. **Интеграционные тесты** *(если останется время)*
    Через тестовый HTTP-клиент и тестовую БД.
    `backend/tests/integration/`

14. **README**
    Отдельный раздел с объяснением выбора архитектуры: почему DI/repository/тесты, и кратко — как выглядел бы более простой вариант без них, чтобы показать осознанность выбора.
    `README.md`

---------- BACKEND

1. Ввод Unit of Work. Цель — убрать разрозненные async with async_session_maker() в каждой функции сервисного слоя, дать единую транзакцию на запрос.
   src/app/core/uow.py — UnitOfWork, репозитории доступны как uow.files/uow.alerts, commit один раз при выходе из контекста.

2. Ввод BaseRepository. Цель — убрать дублирование CRUD-кода, который раньше писался вручную в каждой функции сервисов (session.get, session.add, session.delete и т.д.).
   src/app/repositories.py — BaseRepository с generic CRUD (get_by_id, get_multi, create, update, delete), от него наследуются FileRepository, AlertRepository.

3. Внедрение DI. Цель — убрать создание сервисов и подключений к БД вручную внутри каждого эндпоинта.
   src/app/core/dependencies.py — DI в стиле FastAPI, сервисы (FileService, AlertService) отдаются эндпоинтам через Depends().

4. Перевод сервисного слоя на UoW/DI. Цель — сервисы больше не знают про сессию/движок БД напрямую, вся работа с БД идёт через UnitOfWork.
   src/app/services.py — FileService, AlertService принимают UnitOfWork через конструктор, вся логика (список файлов, создание, апдейт, удаление) переписана на uow.files/uow.alerts.

5. Src-layout и плоские модули. Цель — убрать разрозненную структуру (service.py, ручные пути, импорты из src.*), привести к стандартной структуре Python-пакета.
   src/app/ — весь код перенесён в src-layout, service.py переименован в services.py, конфигурация/БД/Celery разнесены по core/.

6. Исправление бага: удаление файла с алертами. Было: FileService.delete_file падал с ForeignKeyViolationError, если у файла уже были связанные Alert.
   src/app/services.py, FileService.delete_file — перед удалением файла теперь удаляются связанные алерты (uow.alerts.get_multi + uow.alerts.delete в цикле).

7. Написание тестов. Было: тестов не существовало вообще, поведение системы никак не проверялось.
   tests/unit/ — юнит-тесты сервисов (test_file_service.py, test_alert_service.py, test_tasks.py).
   tests/integration/ — интеграционные тесты поверх реального Postgres/Redis/Celery-воркера (testcontainers, override get_uow), 19 тестов, все проходят стабильно, включая ранее нестабильный test_pagination_limit.

8. Неочевидная оптимизация (бонус по ТЗ). Было: обработка файла — три отдельных Celery-таска (скан → метаданные → алерт), каждый со своей транзакцией БД и вызовом .delay() следующего — 3 похода в очередь Redis + 3 commit'а на один файл, хотя это один логический процесс.
   src/app/tasks.py — объединено в один таск _process_file, одна транзакция через UnitOfWork, commit один раз в конце. Бизнес-логика не менялась.


---------- Неочевидная оптимизация

Проблема: сканирование, метаданные и алерт были тремя отдельными Celery-тасками — каждый со своей транзакцией БД и вызовом .delay() следующего. На 1 файл — 3 похода в Redis + 3 commit'а, хотя это один логический процесс.

Фикс: объединили в один таск, одна транзакция через UnitOfWork, commit один раз в конце.
Итог: 3 транзакции + 3 сообщения в очередь → 1 и 1.
